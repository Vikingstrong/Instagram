# Coins — кошелёк, ежедневный бонус и интеграция с Live

Реализованы CoinsModule, миграция, browser-safe контракты, Swagger и страница
`/coins`. Продуктовые правила: [FR-14](../product/PRD.md#fr-14--золотые-коины-и-подарки-в-эфирах)
и [план Coins](../product/coins.md). Настоящие эфиры, каталог подарков,
публичная отправка подарка и её UI остаются задачами разработчика Live.

## Правила и хранение

- Новый кошелёк имеет баланс 0. Чтение не создаёт кошелёк и не начисляет бонус.
- `POST daily-claim` вручную начисляет 100 коинов один раз за календарную дату
  `Asia/Dushanbe` (UTC+5). Смена даты происходит в 19:00 UTC, то есть в 00:00
  следующей даты Душанбе. Накопленный баланс не сбрасывается.
- Дата определяется сервером **после** получения блокировки кошелька. Клиент
  не передаёт дату, сумму, часовой пояс или получателя начисления.
- Суммы в PostgreSQL — BIGINT, в JSON — неотрицательные десятичные **строки**,
  например `"100"`. Максимум `9223372036854775807`; без float и потери точности
  в браузере. Цена подарка положительна, получатель получает её полностью.
- `coin_wallets` хранит баланс; `coin_operations` — журнал бонусов и переводов,
  календарную дату бонуса, участников, исторические балансы после операции,
  контекст подарка и ключ повторного запроса.
- SQL CHECK защищает знак баланса/суммы и форму операций. Unique по аккаунту
  и дате исключает повторный бонус; unique по отправителю и ключу — повторный
  перевод. Блокировки кошельков берутся в одинаковом порядке UUID.
- Журнал ссылается на пользователей с `ON DELETE RESTRICT`. Это не реализация
  удаления аккаунта: политика retention остаётся отдельным решением P-11.
  Тестовые аккаунты удаляются после явной очистки только их тестовых операций.

## Публичный API

Все маршруты требуют подтверждённой cookie-сессии, возвращают `no-store` и
работают только с текущим аккаунтом. Общий error envelope и локализованные
ошибки сохранены. Чтение ограничено 300 запросами за 5 минут на аккаунт;
получение — 30 за 5 минут, плюс существующий mutation-IP limiter.

| Метод | Маршрут | Поведение |
| --- | --- | --- |
| GET | `/api/v1/coins/wallet` | Баланс, серверное время, доступность и время следующего бонуса |
| POST | `/api/v1/coins/daily-claim` | JSON `{}`, Origin и `X-CSRF-Token`; 200 как для нового начисления, так и повтора |
| GET | `/api/v1/coins/transactions?limit=20&cursor=…` | Только своя история, новые первыми; `limit` 1–50; keyset cursor |

Сначала получить CSRF через `GET /api/v1/auth/csrf`, сохраняя cookie.
Swagger `/api/docs/` подготавливает токен автоматически и включает все три
операции. Контракты экспортируются из `@instagram/contracts`:
`CoinWalletResponseSchema`, `CoinClaimResponseSchema`,
`CoinTransactionsResponseSchema`, `CoinGiftReceiptSchema`, `coinsEndpoints`.
Web-обёртка: `apps/web/lib/api/coins.ts`, `createCoinsClient()`.

Пример кошелька до получения:

```json
{
  "wallet": {
    "balance": "0",
    "serverTime": "2026-10-24T10:00:00.000Z",
    "dailyReward": {
      "amount": "100",
      "timeZone": "Asia/Dushanbe",
      "claimed": false,
      "nextClaimAt": "2026-10-24T19:00:00.000Z"
    }
  }
}
```

Получение возвращает `{ credited, wallet, transaction }`. При повторе за ту
же дату `credited=false`, возвращаются прежняя операция и актуальный кошелёк.
Ответ, потерянный в сети, можно безопасно повторить. Время устройства не влияет
на право получения. История содержит `daily_reward`, `gift_sent`, `gift_received`,
положительную строку `amount`, собственный `balanceAfter`, время, публичную
карточку контрагента (или null) и контекст подарка (или null). `balanceAfter`
является историческим значением, а не заменой текущему балансу.

## Для разработчика эфиров

Импортировать `CoinsModule` в Live-модуль и внедрить `CoinsService`.
`transferGift(tx, command)` — реализованный **внутренний серверный метод**,
проверенный на настоящей PostgreSQL. Публичного свободного перевода монет нет.

Команда содержит:

| Поле | Кто определяет |
| --- | --- |
| `senderId` | Проверенная сессия отправителя |
| `recipientId` | Автор доступного эфира из серверной записи Live |
| `amount` | Цена разрешённого подарка из серверного каталога, десятичная строка |
| `streamId` | UUID проверенного эфира |
| `giftKey` | Стабильный ключ подарка, 1–80 символов |
| `idempotencyKey` | UUID одного намерения отправки; повтор сохраняет тот же ключ |

Live обязан внутри **той же транзакции** проверить актуальные права и
жизненный цикл эфира, определить получателя и цену, вызвать перевод и сохранить
свою запись подарка при необходимости. Названия методов Live ниже иллюстрируют
будущую интеграцию, они ещё не реализованы:

```ts
return prisma.$transaction(async (tx) => {
  const stream = await live.lockAccessibleActiveStream(tx, actorId, streamId);
  const gift = await catalog.getAvailableGift(tx, giftKey);
  return coins.transferGift(tx, {
    senderId: actorId,
    recipientId: stream.authorId,
    amount: gift.coinPrice.toString(),
    streamId: stream.id,
    giftKey: gift.key,
    idempotencyKey,
  });
});
```

- Списание, полное зачисление автору и запись перевода выполняются атомарно.
  Метод отклоняет обычный PrismaClient: нужен клиент интерактивной транзакции.
  Ошибка должна выйти из callback транзакции: нельзя перехватить её внутри и
  затем закоммитить частичные изменения. Проверен и откат после успешного
  вызова Coins при последующей ошибке Live.
- Повтор с тем же отправителем, ключом и параметрами возвращает прежний
  `{ receipt, replayed: true }`. Другие параметры с тем же ключом дают
  `COINS_OPERATION_CONFLICT` (409). Контекст/цена повторяемого намерения должны
  оставаться стабильными; нельзя генерировать новый ключ при сетевом retry.
- Receipt содержит id, сумму, senderId, recipientId, streamId, giftKey и время.
  Чужие балансы в receipt не входят. Рассылка SSE/UI происходит после commit;
  уведомление не является повторной денежной операцией. Надёжная доставка
  Live-уведомлений выбирается в Live-срезе.
- `COINS_INSUFFICIENT_BALANCE` и `COINS_BALANCE_LIMIT` имеют статус 409.
  Неверная внутренняя команда и self-transfer отклоняются. Подарки себе не
  реализованы; их продуктовая политика остаётся открытой.
- Сейчас `streamId` — контекст UUID без FK к несуществующей таблице Live.
  При добавлении модели эфиров нужно согласовать связь и retention, проверить
  право/состояние и не выдавать метод Coins за такую проверку.
- Каталог/цены, отмена/возвраты и гонка завершения эфира — открытые решения.
  Этот PR не создаёт фиктивный Live endpoint или неработающую кнопку подарка.

## Интерфейс

Пункт «Получить монеты» в «Ещё» показывает актуальный баланс при открытии и
ведёт на `/coins`; доступен в desktop rail и мобильной шапке. Кошелёк показывает
баланс, бонус, дату следующего получения по Душанбе и историю с пагинацией.
Акцент — на цифрах и действиях: текстовый заголовок, без emoji и больших иконок.
Фото золотых монет с Instagram-глифом сгенерировано для проекта и хранится в
`apps/web/public/coins/instagram-coins.png`; Next Image оптимизирует статический
декоративный asset. Защищённые пользовательские media этим способом не выдаются.
`images.localPatterns` разрешает оптимизацию только `/auth-art/**` и `/coins/**`
без query string; запрос к оптимизатору с API media отклоняется ещё до загрузки.

Нет оптимистического увеличения баланса. Неудача сохраняет старое значение,
повтор обращается к API. При смене аккаунта/проверке сессии данные скрываются,
поздние ответы отменённых запросов игнорируются. Кошелёк перепроверяется при
возврате в приложение, раз в минуту в видимой вкладке и на серверной границе
суток; успешный claim также обновляет таймер. Баланс из старого фонового
запроса не перезаписывает результат начисления.

## Миграция и проверки

Миграция `20261024140000_coins` добавляет две таблицы и enum; новые кошельки
не создаются массово и существующие аккаунты не получают автоматический бонус.
Применить отдельно к dev и test:

```sh
pnpm --filter @instagram/api db:migrate:deploy
pnpm --filter @instagram/api db:migrate:test
```

Проверки реализованы в `coins.integration-spec.ts`, `coin-clock.spec.ts`,
contracts `coins.test.mjs`, web `coin-wallet.test.tsx` и Playwright `coins.spec.mts`.
Они покрывают конкурентные бонусы, блокировку на границе суток, повтор/конфликт
перевода, overdraft/overflow, встречные переводы, откат, bigint precision,
SQL-инварианты, приватную пагинацию, Origin/CSRF, потерю ответа, смену аккаунта,
переход суток независимо от часов устройства и реальный web → API → БД сценарий.
Фактические результаты проверок фиксируются в PR. Приёмка физического телефона,
двух реальных ПК/FND-08 и будущего Live через реальные сети остаётся отдельной.

денежный примитив в реальной PostgreSQL, а не имитация готового Live.
