# Подготовка этапа 2 — Auth и email

Статус: подготовка контракта для review, не работающая авторизация.
Решения владельца проекта: [PRD FR-01](../product/PRD.md#fr-01--authentication--email-verification),
P-01/P-02/P-03 и auth-часть P-09. PR #9 объединён в `main`.

## Что подготовлено

`packages/contracts/src/auth.ts` содержит browser-safe Zod-схемы полей,
строгих запросов регистрации и входа, а также выведенные TypeScript-типы.
Схемы экспортируются из `@instagram/contracts`; API и формы пока их не используют.
Изменение аддитивное, readiness/error контракт не меняется. Новых HTTP routes,
Prisma-моделей, миграций, SMTP-адаптера или независимой Next.js auth-системы нет.

| Поле | Подготовленное правило |
| --- | --- |
| Username | 3–30 ASCII-символов: латинские буквы, цифры, `_`, `.`; регистр ввода сохраняется |
| Email | Формат `z.email()`, не более 254 символов; ввод не обрезается и не переписывается |
| Пароль | 12–128 Unicode code points; пробелы разрешены, нет обязательных классов символов; без trim/нормализации |
| Запрос регистрации | Только `email`, `username`, `password` |
| Запрос входа | Предложение первого среза: `email`, `password`; требует review контракта |

Code points — техническая единица подсчёта, а не визуальные символы: emoji вне
BMP считается один раз, комбинируемые знаки и составные emoji могут занимать
несколько code points. Непарные UTF-16 surrogate отклоняются. HTML `minlength` /
`maxlength` считает UTF-16 units и не должен подменять общую схему в форме.
Проверка длины не означает проверку стойкости пароля.

Запросы отклоняют неизвестные поля, включая `role`, `emailVerified` и
`passwordHash`. Нельзя логировать исходный payload или Zod error вместе с
пользовательским вводом: запрос содержит пароль.

Уникальность не проверяется Zod. Username должен получить регистронезависимый
уникальный ключ в PostgreSQL. Нормализацию email и ключи идентичности ещё нужно
зафиксировать в persistence-контракте; не удалять точки и `+suffix` по правилам
отдельных почтовых провайдеров. До review этих правил регистрационный service
не реализуется. Текущие input-схемы — материал для согласования обоих разработчиков.

## Порядок дальнейшей реализации

1. Провести [приёмку FND-08](foundation-acceptance.md). Подготовка схем и тестов
   не снимает требования запуска на машинах обоих разработчиков. Зависимая
   реализация Auth начинается после приёмки Foundation и review контракта.
2. Согласовать первый HTTP-срез регистрации/входа: нормализацию email, ключи
   уникальности, ответы, безопасные ошибки, поведение при повторной регистрации,
   cookie/CSRF handshake, Origin-проверки. Не объявлять существующий
   `ApiErrorResponseSchema` готовым для Auth: он содержит только readiness 503.
3. До кода зафиксировать технические параметры: библиотеку и параметры
   хеширования паролей, сроки сессий и отдельных одноразовых токенов, лимиты
   запросов и размер тела, SMTP-конфигурацию и durable retries в PostgreSQL.
   Не добавлять Redis или иной сервис. Cookie, токены и CSRF не хранятся
   в localStorage и не экспортируются как внутренние модели в contracts.
4. Добавлять API, Prisma-миграции, схемы ответов, fixtures и тесты одним срезом;
   после review контракта frontend использует те же схемы. Swagger обновляется
   вместе с реальными endpoints, не описывает ещё несуществующие handlers.
5. Добавить verification/recovery и повторную отправку писем через MailModule.
   Mailpit используется локально; для размещённой демоверсии нужны отдельные
   SMTP-провайдер, секреты и проверка доставки. Открытая регистрация — целевой
   режим, но публичный запуск принимается отдельно на этапе 8.

## Тесты перед приёмкой Auth

Эти сценарии пока не реализованы и не засчитываются как PASS:

- Реальные миграции PostgreSQL, уникальность и конкурентная регистрация.
- Подтверждение email, срок/одноразовость токенов, повторная отправка и сбой SMTP.
- У неподтверждённого пользователя нет доступа к защищённым данным даже через
  прямой API-запрос; ответы не раскрывают внутренние поля и существование email
  в восстановлении.
- CSRF/Origin, cookie в dev/HTTPS, rate limits и безопасные ошибки.
- Logout отзывает конкретную сессию. Успешный reset атомарно меняет пароль,
  погашает применимые recovery-токены и отзывает все сессии, включая текущую;
  конкурентные reset и login не должны оставлять сессию со старым паролем.
- После reset первый срез требует нового входа. Будущий автовход — отдельная
  задача с выдачей новой сессии API после отзыва старых.
- Полный browser-flow двух независимых пользователей через реальные письма
  Mailpit; очистка клиентского кеша после logout/смены пользователя, SSR-контекст
  сессии без общего кеша. Не очищать общий mailbox параллельных запусков.

На реальных ноутбуках до разработки/интеграции зависимого Auth-среза сначала
нужно пройти Foundation-чек-лист. После реализации Auth его прикладные сценарии
проверяются дополнительно: readiness и контрактные unit-тесты не доказывают
работу регистрации, сессий или отправки писем.
