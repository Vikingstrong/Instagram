## Как устроено

- Видео: WebRTC из браузера ведущего каждому зрителю (fan-out, одно
  `RTCPeerConnection` на зрителя). Зритель делает offer только на приём,
  ведущий отвечает и отправляет всем одни и те же треки, до 1 Мбит/с видео
  на зрителя. Через API видео не идёт и нигде не хранится.
- API (`LivesModule`) ведёт состояние эфира, зрителей, сигналы и чат.
  Эфир и чат — в PostgreSQL, зрители и SDP/ICE — в памяти единственного
  процесса API (как буфер сигналов звонков).
- Сигнализация — REST + общий SSE-поток вкладки `/api/v1/direct/events`:
  событие `live` содержит только `{ liveId }`, состояние читается по REST.
  В web поток открывает provider звонков, он же пересылает `live` в
  интерфейс эфиров: второй поток на вкладку не открывается (лимит 5 на
  пользователя). Polling раз в 1,5 с (сигналы) и 2 с (чат) — страховка.
- ICE/TURN — та же конфигурация `CALLS_*` и временные credentials, что у
  звонков (`GET /api/v1/lives/config`). В production без TURN старт и вход
  в эфир закрыты `503 LIVES_UNAVAILABLE`.

## Права и безопасность

- Смотреть, читать и писать чат может тот, кто видит публикации автора:
  `visibleAuthor` из `post-policy.ts` (сам автор, публичный профиль,
  одобренная подписка; ожидающий запрос не даёт ничего). Право
  проверяется на каждом запросе зрителя и раз в 5 с для всех подключённых.
  Отписка, удаление подписчика или закрытие профиля во время эфира
  отключают зрителя; ведущий закрывает его соединение при следующей
  синхронизации, сигналы и чат отвечают 404.
- Закрытый аккаунт не раскрывает факт эфира: `GET /lives/host/{id}`
  возвращает `null`, `GET /lives/{id}` — `404 LIVE_NOT_FOUND`.
- Начать и завершить эфир может только автор. Соединение ведущего и
  зрителя привязано к пользователю, хешу серверной сессии и UUID вкладки;
  UUID не является авторизацией. offer шлёт только зритель, answer —
  только ведущий, ICE — оба; чужой `peerId` — 409.
- Один эфир на автора (`activeHostId` с уникальным индексом), один
  зритель — одно соединение (новая вкладка вытесняет старую), не больше
  10 зрителей (`409 LIVE_FULL`).
- Все мутации требуют Origin, CSRF и JSON; ответы `no-store`. Лимиты:
  10 стартов в час, 30 сообщений чата в минуту, 400 мутаций и 600
  чтений в минуту на пользователя, 5000 мутаций за 5 минут на IP.
- SDP/ICE не пишутся в БД и логи; непрочитанные сигналы ограничены
  (256 и 256 Ki символов на зрителя, 2048 и 1 Mi у ведущего) и удаляются
  после подтверждения курсором или ухода зрителя.

## Жизненный цикл

- «Готовится» — клиентский шаг: выбор камеры и микрофона, предпросмотр.
  На сервере эфир сразу `LIVE`; повтор `POST /lives` с тем же id и
  устройством возвращает тот же эфир.
- Heartbeat ведущего и зрителей — раз в 5 с. Ведущий без heartbeat 20 с,
  эфир дольше 60 минут, logout или сброс пароля ведущего завершают эфир
  (`endReason`: LOST, TIME_LIMIT, SIGNED_OUT; HOST — сам автор). Уход
  со страницы эфира в приложении тоже завершает его; закрытая вкладка —
  через 20 с.
- При завершении чат удаляется в той же транзакции, все зрители и
  подписчики получают `live`; зритель видит «Эфир завершён». Завершённые
  эфиры (без видео и чата) хранятся сутки, чтобы опоздавший увидел статус.
- Зритель без heartbeat 20 с или после logout отключается. Сбой
  соединения, `disconnected` дольше 5 с, нет соединения через 20 с после
  входа, перезапуск API или вытеснение другой вкладкой — зритель
  автоматически входит заново с новым `peerId` (не чаще раза в 3 с).

## REST

- `GET /api/v1/lives` — эфиры подписок и свой; `GET /lives/current` — свой.
- `GET /lives/host/{userId}` → `{ live | null }`; `GET /lives/config` — ICE.
- `POST /lives { id, clientId }` → 201; `GET /lives/{id}`; `POST /lives/{id}/end {}`.
- `POST /lives/{id}/join|leave|heartbeat { clientId }`; join → `{ live, peerId }`.
- `POST /lives/{id}/signals { clientId, peerId, signal }`,
  `GET /lives/{id}/signals?clientId&after` → `{ items, peers, next }`
  (`peers` с профилями зрителей — только ведущему).
- `GET /lives/{id}/comments?after` — последние 50 или следующие после
  курсора; `POST /lives/{id}/comments { id, text }` → 201, идемпотентно.

Схемы — `packages/contracts/src/lives.ts`. Новые ошибки: `LIVE_NOT_FOUND`,
`LIVE_BUSY`, `LIVE_FULL`, `LIVE_ENDED`, `LIVE_STATE_CONFLICT`,
`LIVES_UNAVAILABLE`. Миграция `20261024120000_live_streams` добавочная.

## Web

- `/live` — ведущий: выбор камеры и микрофона, предпросмотр, «Начать
  эфир», затем время в эфире, число и список зрителей, чат, выключение
  микрофона и камеры, «Завершить». Ошибки устройств — общие тексты звонков.
- `/live/{id}` — зритель: плеер, «Подключаемся / Переподключаемся», «Эфир
  завершён», «Эфир недоступен», «максимум зрителей», ручное включение
  звука, если браузер запретил автозапуск со звуком.
- Кольцо «В эфире» на аватаре профиля, полоса эфиров подписок на главной,
  уведомление «… начал(а) прямой эфир» подписчикам, ссылка на странице
  «Создать».
- `live-transport.ts` (WebRTC) и `viewer-session.ts` (жизненный цикл
  зрителя) не зависят от React; транспорт заменяется адаптером SFU.

## Ограничения

- Fan-out нагружает исходящий канал и CPU ведущего, поэтому 10 зрителей.
  Для большего числа нужен SFU — решение этапа 12 вместе с хостингом.
- Без TURN зрители за NAT не подключатся; реальная проверка NAT/TURN —
  этап 12, как у звонков.
- Сигнализация и зрители в памяти: несколько экземпляров API не
  поддерживаются (как SSE hub и звонки).
- После перезагрузки страницы ведущий не продолжает тот же эфир: его
  можно завершить и начать новый.
- Маршрут `/live` занимает имя пользователя `live` так же, как `/reels` и
  `/direct` — общий вопрос зарезервированных имён.
