# Posts API — публикации, аватары и приватные изображения (этап 4)

Backend этапа 4: одна фотография на пост, аватар, защищённая выдача файлов и
очистка. Frontend этапа — следующий срез. Решения приняты Developer 2 соло
2026-10-23, пока Developer 1 недоступен; требуют review в PR.

## Решения

| Вопрос | Решение |
| --- | --- |
| P-08 форматы и лимиты | JPEG, PNG, WebP; до 10 МБ и 40 млн пикселей; одно неанимированное изображение |
| P-09 подпись | 0–2200 code points, переводы строк разрешены, управляющие символы — нет |
| Приём файла | `multer` из `@nestjs/platform-express`, только в памяти, лимиты до разбора тела |
| Обработка | `sharp` 0.35: проверка декодируемого содержимого (не имени и не `Content-Type`), поворот по EXIF, удаление метаданных, перекодирование в WebP; не более 2 обработок одновременно |
| Варианты | `full` — вписано в 1080×1350 без увеличения; `thumb` — квадрат 480×480 (`cover`) |
| Хранилище | Локальный приватный адаптер (`MEDIA_ROOT`, по умолчанию `<repo>/.local/media`, вне Git и публичных папок). Интерфейс `MediaStorage` позволяет заменить его на объектное хранилище |
| Выдача | Только через API с проверкой прав на каждый запрос; `Cache-Control: private, no-store`, `nosniff`; без публичных и подписанных URL |
| Аватар | Виден везде, где видна сводка профиля (FR-02), в том числе у закрытого аккаунта |
| Поиск по имени | Исправлено попутно: ключ `displayNameKey` (Unicode lower case в API), т. к. collation `C` не сворачивает кириллицу |

## База

- `20261023080000_display_name_key` — `auth_users.displayNameKey` для поиска
  без учёта регистра; заполнение через ICU, если сервер его поддерживает.
- `20261023090000_posts_media`:
  - `media`: владелец, вид `POST | AVATAR`, состояние
    `PENDING | READY | DELETED`, размеры, `deletedAt`. CHECK: у `READY` есть
    размеры, `deletedAt` есть ровно у `DELETED`.
  - `posts`: автор, `mediaId` (уникален, `NO ACTION`), подпись, время; индекс
    `(authorId, createdAt DESC, id DESC)`.
  - `auth_users.avatarMediaId` (уникален, `SET NULL`).

## Жизненный цикл файла

1. Изображение проверяется и готовится до записи в БД — ошибка не оставляет
   ничего.
2. Создаётся `PENDING`-запись, пишутся файлы.
3. Одна транзакция переводит медиа в `READY` и создаёт пост (или ставит
   аватар). Ошибка → медиа `DELETED`, файлы удаляются, поста нет.
4. Удаление поста/аватара: в транзакции медиа → `DELETED` (выдача
   прекращается сразу), затем файлы и запись удаляются.
5. Очистка каждые 10 минут (`MEDIA_CLEANUP_ENABLED`) повторно удаляет
   `DELETED` и `PENDING` старше часа. Повторный запуск безопасен.

## Запросы

Все требуют подтверждённую сессию; мутации — Origin + CSRF. Загрузка —
`multipart/form-data`, поле `image`; тело JSON `{}` для удалений.

| Метод | Путь | Ответ / ошибки |
| --- | --- | --- |
| POST | `/api/v1/posts` | `201 { post }`; поля `image`, `caption?`. `400 INVALID_IMAGE` (нет файла, не изображение, другой формат, анимация, больше 40 Мп), `413 IMAGE_TOO_LARGE`, `400 INVALID_REQUEST` (подпись, лишние поля) |
| GET | `/api/v1/posts/{id}` | `{ post }`: автор (карточка), подпись, `image { url, thumbnailUrl, width, height }`, `createdAt`. Скрытый/удалённый — `404 POST_NOT_FOUND` |
| DELETE | `/api/v1/posts/{id}` | `{ status: "deleted" }`; чужой пост — `404` |
| GET | `/api/v1/users/{id}/posts` | `{ items: Post[], nextCursor }`, новые сверху; закрытый профиль без доступа — `403 PROFILE_PRIVATE` |
| PUT | `/api/v1/me/avatar` | `{ avatarUrl }`; старый аватар перестаёт выдаваться |
| DELETE | `/api/v1/me/avatar` | `{ avatarUrl: null }` |
| GET | `/api/v1/media/{id}/{full\|thumb}` | `image/webp` после проверки прав; иначе `404 MEDIA_NOT_FOUND` |

Правило видимости одно (`posts/post-policy.ts`): автор, публичный профиль или
одобренная подписка; ожидающий запрос не даёт доступа. Оно применяется в SQL
к посту, сетке профиля и каждому файлу, поэтому удаление подписчика сразу
закрывает и прямые ссылки на изображения. `counts.posts` в профиле публичен.
