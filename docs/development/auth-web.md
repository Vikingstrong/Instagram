# Этап 2 — формы регистрации, входа и состояние сессии

Frontend использует существующие Auth-контракты и настоящий API. Новых схем,
зависимостей, миграций или Next.js authentication backend нет.
Требования: [PRD FR-01](../product/PRD.md#fr-01--authentication--email-verification),
[архитектура §8](../architecture/overview.md#8-authentication-and-session-architecture),
[Auth API](auth-api.md).

## Поведение

- `/auth/register`: username/email/password проверяются общими Zod-схемами.
  Unicode-пароль и пробелы сохраняются; HTML maxlength для пароля не используется,
  поскольку он считает UTF-16 units вместо согласованных code points.
- Успешная регистрация входит в новый неподтверждённый аккаунт и открывает
  `/auth/session` («Подтвердите email»). Изменено 2026-10-22, см. раздел ниже;
  сообщение об отправке письма — не обещание успешной доставки SMTP.
- `/auth/login`: вход через API cookie-сессию. Ошибки локализуются по code;
  raw message, requestId и внутренние данные не выводятся. Повторная отправка
  блокируется, пока запрос выполняется; mutations автоматически не повторяются.
- `/auth/session`: свежий GET с `no-store`, состояния loading/error/anonymous/
  user, требование подтверждения email для неподтверждённого аккаунта и выход.
  Ссылка «Аккаунт» в desktop/mobile навигации ведёт на эту страницу.
- Каждая mutation сначала получает новый CSRF через API. Пароли удаляются из
  поля после попытки отправки; cookies и токены не сохраняются в localStorage
  или sessionStorage. HttpOnly-cookie создаёт и отзывает только API.
- После входа/выхода выполняется полная document navigation, сбрасывающая
  предыдущий React/router state. Нет общего кеша пользователя. При focus,
  pageshow и возвращении вкладки сессия перечитывается; старое имя скрывается
  на время проверки. Устаревшие ответы отменённых запросов игнорируются.
  Выход очищает отображаемую identity до запроса; при ошибке не заявляется,
  что серверная сессия уже отозвана, и доступна повторная попытка.

## Обновление интерфейса и гостевой режим — 2026-10-22

По указанию владельца Auth-страницы используют общий адаптивный split layout:
композиция карточек на desktop, компактная форма на mobile. Отправка и пароли
остаются в том же API-контракте; добавлен показ/скрытие пароля. Общий минимум
регистрации/login/reset снижен с 12 до 8 Unicode code points, максимум 128;
обновлены Zod/OpenAPI metadata, подсказки и boundary tests. Миграций нет.

После регистрации показывается «Подтвердите email» (автовход добавлен позже,
см. следующий раздел); запись БД остаётся pending, защищённые операции
запрещены до однократного подтверждения.
Вход подтверждённого аккаунта ведёт на `/` без повторного письма, вход
неподтверждённого — в `/auth/session` с resend/logout. API verified guard не менялся.

Главная сначала запрашивает свежую API-сессию. Без сессии направляет на вход;
«Продолжить как гость» открывает `/?guest=1`. Гость просматривает существующую
ленту без постоянного баннера. Попытка взаимодействия с публикацией, подписки,
комментария или перехода к сообщениям вызывает модальное приглашение войти
или зарегистрироваться. Escape/кнопка закрытия возвращает к просмотру; native
`dialog` удерживает фокус. Гостевая cookie/API identity не создаётся.

URL-параметр — только выбор интерфейса, не серверное разрешение. Текущая лента
по-прежнему использует макетные данные; права чтения будущих реальных профилей,
media и ленты определяются на этапах 3–5. Правая колонка больше не выдаёт
фиктивного `your.username` за текущий аккаунт: identity берётся из сессии,
у гостя персональный блок скрыт. При focus/pageshow/visibility сессия проверяется
заново, прежняя identity скрывается, устаревшие ответы игнорируются; смена
пользователя сбрасывает дочернее состояние. Ошибка API не считается гостевым входом.

Проверка доступа и shell находятся внутри home page, а layout всегда отдаёт
route children. Это сохраняет [проверку instant navigation Next.js](https://nextjs.org/docs/messages/instant-unrendered-segment)
без отключения её диагностики. Новых зависимостей и инфраструктуры нет.

Локальная ошибка входа диагностирована как readiness 503: настроенный native
PostgreSQL на 55432 был остановлен. После запуска readiness вернул 200. Для
ручной регистрации настроен приватный `.env` с постоянным outbox key/SMTP,
запущен локальный Mailpit 1025/8025 и применены обе существующие добавочные
миграции к dev-БД, без reset. Секреты и runtime PostgreSQL не входят в срез.

Проверки нового среза выполнены в отдельном checkout с копией итоговых
исходников, PostgreSQL 18.6 на 55442 и Mailpit 11042/18042. Browser API обслуживал
TEST-базу на 4100, web — 3100; в копии изменены только порты Playwright/Swagger.

## Вход после регистрации и подтверждение email — 2026-10-22

Решение Developer 2 (UX); требует review тимлида в PR.

- `POST /auth/register` в одной транзакции создаёт аккаунт, verification-токен,
  задание письма и сессию; cookie ставится с теми же флагами, что при login.
  Неподтверждённая сессия, как и раньше, не открывает защищённые операции:
  verified guard не менялся.
- После регистрации — сразу `/auth/session` «Подтвердите email» с адресом
  аккаунта. «Отправить письмо повторно» использует email сессии, без отдельной
  формы. `/auth/request-verification` остаётся для вышедших из аккаунта и
  подставляет email, если сессия есть.
- Ссылка из письма после подтверждения ведёт сразу на `/`: подтверждённая сессия
  видит ленту, без сессии главная направляет на вход. Ссылка «Проверить сессию»
  удалена. Если подтверждение произошло в другой вкладке, `/auth/session`
  при возврате фокуса переводит в ленту.
- Вход с неизвестным email по-прежнему даёт общий `INVALID_CREDENTIALS`
  («Неверный email или пароль») — без раскрытия существования аккаунта.
  Под ошибкой добавлена ссылка «Нет аккаунта? Зарегистрируйтесь».
- Переходы после auth вынесены в `lib/navigation.ts` (`replaceLocation`), чтобы
  тесты проверяли их без навигации jsdom.
- E2E-хелпер `e2e/helpers/auth-api.mts` останавливает изолированный API через
  IPC-сообщение вместо SIGTERM: на Windows SIGTERM не перехватывается, процесс
  завершался без удаления тестового аккаунта и с ошибкой cleanup.
