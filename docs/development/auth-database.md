# Этап 2 — БД Auth: первый срез

Владелец 2026-10-22 разрешил начать реализацию этапа 2 до завершения FND-08.
Проверки на двух реальных ПК и совместная приёмка остаются открытыми и нужны
до окончательного закрытия этапа 2. Это изменение порядка не означает PASS
для непроверенных критериев Foundation.

## Объём реализации

Prisma schema и первая миграция
`apps/api/prisma/migrations/20261022060000_auth_database/migration.sql`
создают только слой хранения Auth. Пользовательские HTTP endpoints, cookie/CSRF,
хеширование пароля, SMTP и формы ещё не реализованы. Swagger продолжает
описывать существующий readiness, а не будущие Auth endpoints.

| Модель / таблица | Назначение |
| --- | --- |
| `User` / `auth_users` | UUID, исходные email/username и уникальные ключи, хеш пароля, подтверждение email, версия учётных данных, даты |
| `AuthSession` / `auth_sessions` | Пользователь, SHA-256 хеш непрозрачного токена, снимок версии учётных данных, срок и отзыв |
| `AuthToken` / `auth_tokens` | Пользователь, назначение verification/reset, SHA-256 хеш, снимок версии, срок, погашение или отзыв |

Связи с пользователем имеют FK; физическое удаление строки пользователя удаляет
её сессии и токены. Это поддержка целостности и изолированной очистки тестов,
не продуктовая реализация удаления аккаунта: P-11 по-прежнему открыт.
Индексы обслуживают поиск по хешу, отзыв сессий пользователя, токены по
пользователю/назначению и будущую очистку истёкших записей. Очистка пока не запущена.

## Идентичность и нормализация

Техническое решение этого среза, требующее review обоих разработчиков:

- `email` и `username` сохраняют исходное написание. `emailKey` и `usernameKey`
  содержат ASCII lower-case значения; SQL CHECK связывает ключ с исходным полем
  через `lower(... COLLATE "C")`. Ключи имеют UNIQUE-индексы, поэтому конкурентная
  запись разных вариантов регистра не создаёт два аккаунта.
- `User@example.test` и `user@example.test` — один identity key. Это выбранная
  политика приложения, а не утверждение о правилах всех SMTP-серверов.
  Точки и `+suffix` не удаляются, провайдерские преобразования не применяются.
- Username сохраняет согласованный алфавит и длину 3–30. Подготовленная схема
  email в contracts поддерживает ASCII-формат; Unicode/IDN email этим срезом
  не добавляется. Полную проверку формата email выполняет будущая API-валидация;
  DB CHECK не считается заменой Zod-схемы.
- Пароль не обрезается и не нормализуется. `passwordHash` предназначен для
  кодированного хеша библиотеки, не пароля. CHECK ограничивает размер хеша
  1–1024 байт, но не доказывает корректность хеширования: алгоритм и библиотека
  должны быть выбраны и протестированы до регистрационного service.

Ключи внутренние, не входят в browser-safe contracts. API не должен возвращать
Prisma User целиком: хеши, версии и внутренние поля исключаются явной проекцией.

## Сессии и одноразовые токены

Хеши токенов — 64 символа lower-case hex (SHA-256); исходный токен в таблицах
не хранится. Генерация криптографически случайных токенов и их выдача клиенту
ещё не реализованы. Формат хеша не является доказательством безопасной генерации.

Миграция проверяет неотрицательную версию, `expiresAt > createdAt`, допустимые
даты отзыва/погашения. Токен нельзя одновременно отметить погашенным и отозванным;
погашение допускается только до истечения срока. `AuthTokenPurpose` различает
`EMAIL_VERIFICATION` и `PASSWORD_RESET`. Хеш уникален во всей таблице токенов,
в том числе между назначениями. Сессии имеют отдельный UNIQUE-индекс хеша.

Для будущего API обязательны дополнительные условия, которые **не включаются
автоматически наличием этих колонок**:

1. При выдаче сессии/токена сохранить актуальную `User.credentialVersion`.
   На каждом защищённом запросе проверить срок, отзыв, текущую версию и нужное
   подтверждение email. При изменении пароля увеличить версию; сессия со старым
   снимком недействительна, даже если конкурентный login успел вставить её позже.
2. Погашать токен условным UPDATE по хешу, назначению, версии, сроку и отсутствию
   погашения/отзыва. Результат должен затронуть ровно одну строку. Проверить
   текущую версию пользователя в той же транзакции с действием токена.
3. Успешный reset в одной транзакции погашает предъявленный токен, меняет хеш,
   увеличивает версию, отзывает все сессии и остальные ещё не погашенные recovery
   tokens. Сериализовать reset/выдачу токенов/смену учётных данных блокировкой
   пользователя или эквивалентной проверенной схемой. Отказ транзакции откатывает
   все изменения. В первом срезе после reset требуется новый вход.

Integration-тесты демонстрируют ограничения и атомарные операции PostgreSQL,
но не являются готовым Auth service или доказательством защиты HTTP-запросов.
Нет ещё защиты от перебора, CSRF, доставки писем и автоматического отзыва SSE.
MailModule и его durable retries потребуют отдельного среза/миграции.

## Применение миграции

Сделайте backup, если целевая БД содержит нужные данные; проверьте URL и ожидаемые
существующие таблицы. Это первая аддитивная миграция без DROP/reset/backfill,
предназначенная для текущего Foundation без прикладных таблиц. При конфликте
с уже существующими одноимёнными таблицами не используйте автоматический reset.

Из корня репозитория, по [инструкции БД](database.md):

```bash
pnpm --filter @instagram/api db:validate
pnpm --filter @instagram/api db:generate
pnpm --filter @instagram/api db:migrate:deploy
pnpm --filter @instagram/api db:migrate:test
pnpm --filter @instagram/api test:integration
```

Миграция имеет явную транзакцию BEGIN/COMMIT и проверенный SQL; lock-файл
закрепляет provider PostgreSQL. Она не запускается автоматически при старте API.
Prisma schema не выражает CHECK-ограничения: они являются частью истории SQL
и должны сохраняться в последующих миграциях. `migrate diff` полезен для проверки
поддерживаемой Prisma части схемы, но не заменяет integration-тесты этих CHECK.

Тесты проверяют реальные PostgreSQL FK/UNIQUE/CHECK, гонки уникальности,
условное одноразовое погашение, неподходящие/истёкшие/отозванные токены и rollback
связанных изменений. Cleanup удаляет только UUID пользователей своего запуска,
без глобальных delete/truncate. Отсутствующая конфигурация и отсутствие миграции
должны завершать набор ошибкой, а не SKIP.

Следующий срез: review DB-правил и HTTP-контракта, затем безопасные сервисы
регистрации/сессий с реальными password hashes, API-валидацией и Swagger.

## Проверки — 2026-10-22

Миграции применены только к отдельному новому Docker Compose проекту с
PostgreSQL 18.6, собственным volume, портом и случайными dev/test credentials.
Рабочий корневой `.env` и существующая dev-БД не менялись. Для приватных прав
файлов облачного checkout в этот проект скопирован читаемый init-скрипт; это
не подтверждение чистого запуска на реальных ПК.

| Проверка | Результат |
| --- | --- |
| Prisma validate / generate | PASS |
| Deploy на пустые изолированные dev/test БД | PASS, применена одна миграция |
| Повторный deploy с существующей записью пользователя | PASS, запись сохранена; checksum истории совпал с SQL |
| Prisma schema diff после deploy | PASS, различий поддерживаемой Prisma схемы нет; SQL CHECK проверяются тестами отдельно |
| Реальные PostgreSQL integration | PASS: 16 тестов, из них 10 новых Auth persistence |
| Штатная сборка, типы, линтер | PASS, 0 предупреждений линтера |
| Unit/contracts | PASS: 9 contracts, 8 API, 31 web |
| Существующие API e2e | PASS: 4 теста; это не тесты ещё отсутствующих Auth endpoints |
| Ссылки документации, `git diff --check` | PASS |
| Реальные ПК обоих разработчиков / FND-08 | Не подтверждены |

Настройки зависимостей, shared contracts и runtime endpoints не менялись.
Полный browser/readiness/Swagger набор выполняется в CI PR вместе с миграцией;
результат CI фиксируется в описании PR. Модели БД не означают готовность Auth
или окончательное завершение всех его миграций: MailModule и следующие срезы
могут добавить свою историю.
