# Уведомления о взаимодействиях — 2026-10-24

По запросу владельца уведомления дополняют существующие запросы на подписку.
При лайке публикации и корневом комментарии адресат — автор публикации; при
ответе — автор выбранного комментария (в том числе внутри ветки); при лайке
комментария или ответа — его автор. Собственные действия не уведомляют.

`PostsModule` атомарно записывает взаимодействие и уведомление в PostgreSQL.
Повторный PUT лайка не добавляет дубликат; DELETE лайка удаляет уведомление.
Удаление комментария, ветки, публикации или аккаунта каскадно удаляет
уведомления с неработающими ссылками. Миграция
`20261025100000_interaction_notifications` добавляет таблицу и индекс по
адресату, времени и id; старые данные не удаляет. Старые взаимодействия задним
числом не превращаются в уведомления.

`GET /api/v1/me/notifications?limit=20&cursor=...` возвращает только свои
события, в обратном хронологическом порядке. Видимость публикации проверяется
в SQL до пагинации. Ответы содержат только id, тип события, публичную карточку
автора и дату; текст комментария и cookie не входят в контракт. Экран
`/notifications` сохраняет блок запросов на подписку. Изменения доставляются
по существующему `/api/v1/direct/events` событием `notification` без данных;
клиент затем перечитывает REST. Повторное чтение при открытии вкладки и каждые
30 секунд восстанавливает пропущенные SSE-события и работает при обрыве потока.

Перед деплоем применить миграцию к production-БД командой из запуска Render;
API и web должны быть развёрнуты с одним контрактом. Деплой требует проверки
реальных аккаунтов, приватности и SSE через Vercel/Render: локальные тесты не
подтверждают поведение внешнего прокси.
