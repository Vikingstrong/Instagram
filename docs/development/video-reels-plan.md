## Решения (предложение по P-12)

| Вопрос | Решение |
| --- | --- |
| Входные форматы | MP4, MOV, WebM; проверяется содержимое (ffprobe), не имя и не `Content-Type` |
| Лимиты | До 100 МБ, до 90 с, не больше 4096 px по стороне, обязательна видеодорожка; звук необязателен |
| Результат | H.264 (main) + AAC в MP4, длинная сторона до 1080 px без увеличения, `+faststart`; обложка — кадр 1 с (или первый) в WebP: `full` до 1080×1350 и `thumb` 480×480 через sharp |
| Инструменты | `ffmpeg-static` и `ffprobe-static` (закреплённые версии, одинаковые бинарники локально и в CI); путь можно переопределить `FFMPEG_PATH` / `FFPROBE_PATH` |
| Где обрабатывать | В процессе API, очередь с одной обработкой одновременно и таймаутом 5 мин; без внешнего брокера (архитектура §5) |
| Приём файла | multer с записью во временную папку внутри `MEDIA_ROOT/.incoming` (не в память), лимит размера до разбора тела; файл удаляется после обработки в любом исходе |
| Публикация | Пост создаётся сразу с медиа `PENDING`; правило `visiblePost` уже требует `READY`, поэтому другим он не виден до конца обработки. Автор видит свой пост со статусом `processing` / `failed` |
| Ошибка обработки | Медиа → `DELETED`, пост удаляется, файлы чистятся; автор видит «Не удалось обработать видео» и может загрузить снова |
| Перезапуск API | При старте `PENDING`-видео старше таймаута помечаются ошибкой; периодическая очистка этапа 4 удаляет остатки |
| Выдача | `GET /api/v1/media/{id}/video` с проверкой прав на каждый запрос (как фото), `Accept-Ranges: bytes`, ответы 206 на Range, `Cache-Control: private, no-store`, `nosniff`; обложки — существующие `full` / `thumb` |
| Reels | Видеопосты, доступные зрителю по `post-policy.ts`: свои, одобренных подписок и публичных аккаунтов. Новые сверху, курсор `createdAt, id`, без рекомендаций |
| Лайки и комментарии | Без изменений, общие с фото (FR-06); ответы и счётчики — этап 9 Developer 1 |

Открыто для review: включать ли в Reels публичные аккаунты без подписки
(предложено — да, это «доступные» по FR-10) и лимит загрузок видео
(предложено 10 в час на пользователя).

## Контракт

- `MediaKind` без изменений (`POST`, `AVATAR`); у `media` новые поля
  `type IMAGE | VIDEO`, `durationMs`, `failedAt`.
- `Post` получает `type: "photo" | "video"`, `video: { url, durationMs } | null`
  и `status: "ready" | "processing" | "failed"` (не `ready` — только автору).
  Поле `image` остаётся у всех постов: у видео это обложка, поэтому сетка
  профиля и ленты работают без изменений.
- `MediaUrlSchema` разрешает вариант `video`.
- `POST /api/v1/posts/video` — отдельный путь (фото принимается в память,
  видео сразу пишется на диск); поле `video`, ответ `201 { post }` со
  `status: "processing"`. Превышение размера — `413 VIDEO_TOO_LARGE`.
- `GET /api/v1/reels?cursor&limit` → `{ items: Post[], nextCursor }`.
- Новые ошибки: `INVALID_VIDEO` 400, `VIDEO_TOO_LARGE` 413,
  `VIDEO_TOO_LONG` 400.
- Изменения `PostSchema` согласуются с Developer 1: этап 9 тоже трогает
  посты (счётчики). Правило — каждый добавляет поля, ничего не переименовывая.

## Риски

- Перекодирование нагружает единственный процесс API — одна обработка за
  раз и таймаут; при необходимости вынос в отдельный worker на этапе 10.
- Размер `ffmpeg-static` (~70 МБ) и его загрузка в CI; путь через
  переменные окружения оставляет вариант системного ffmpeg на хостинге.
- Лицензия сборок ffmpeg (GPL) — допустимо для портфолио, указать в README.
- Диск: исходник удаляется сразу, хранится только результат и обложки.
- Конфликты миграций с этапом 9 — у нас только `media`, у Developer 1 —
  комментарии и звонки; порядок миграций по времени слияния.
