## Решения (предложение по P-15)

| Вопрос | Решение |
| --- | --- |
| Транспорт видео | WebRTC из браузера ведущего напрямую к каждому зрителю (fan-out: одно `RTCPeerConnection` на зрителя). Видео не проходит через API и не хранится |
| Почему не SFU | Архитектура §1/§14 фиксирует один процесс API без новых сервисов; SFU (LiveKit, mediasoup) не установлен ни локально, ни в CI, и его выбор зависит от хостинга этапа 12. Клиентский транспорт изолирован (`live-transport.ts`), его можно заменить адаптером SFU без изменения API эфира, чата и прав |
| Сигнализация | Существующие REST + SSE, как у звонков этапа 9: SDP/ICE в памяти процесса, в SSE только `{ liveId }`, polling как страховка. Offer делает зритель (recvonly), answer — ведущий |
| STUN/TURN | Та же конфигурация и временные TURN credentials, что у звонков (`CALLS_*`); в production без TURN старт и вход в эфир закрыты 503 |
| Лимиты | До 10 одновременных зрителей на эфир (исходящий канал ведущего), один эфир на автора, до 60 минут, 10 стартов в час |
| Кто смотрит и пишет в чат | Тот, кто видит посты автора (`visibleAuthor` из `post-policy.ts`): сам автор, публичный профиль, одобренная подписка. Право перепроверяется на каждом запросе зрителя и периодически (раз в 5 с) для всех подключённых |
| Отзыв доступа | Отписка, удаление подписчика или закрытие профиля во время эфира: зритель исключается при следующей проверке, ведущий закрывает его соединение, чат и сигналы отвечают 404 |
| Чат | Сообщения до 300 символов в PostgreSQL на время эфира, удаляются при завершении (эфиры не записываются). Идемпотентность по id клиента, до 30 сообщений в минуту |
| Завершение | Ведущий; потеря heartbeat ведущего дольше 20 с; logout или сброс пароля ведущего; лимит длительности. Зритель исключается при потере heartbeat 20 с, logout и отзыве доступа |
| Уведомление подписчиков | SSE `live` одобренным подписчикам при старте и завершении; в web — всплывающее «начал(а) прямой эфир» и полоса «В эфире» на главной |
| Запись | Нет: ни видео, ни чата после завершения |

Открыто для review: лимит 10 зрителей (при SFU можно больше), 60 минут,
повторный вход ведущего после перезагрузки страницы (сейчас — только
завершение старого эфира и новый старт).

## Контракт

- `LiveStatus`: `LIVE | ENDED`. «Готовится» — клиентский шаг предпросмотра,
  на сервере не хранится.
- `Live`: `{ id, host: UserSummary, status, startedAt, endedAt, viewerCount }`.
- `GET /api/v1/lives` — эфиры подписок и свой; `GET /lives/current` — свой
  активный; `GET /lives/host/{userId}` — эфир автора или `null` без утечки
  факта эфира закрытого аккаунта; `GET /lives/config` — ICE.
- `POST /lives { id, clientId }` → 201; `POST /lives/{id}/end`.
- `POST /lives/{id}/join|leave|heartbeat { clientId }`; join → `{ live, peerId }`.
- `POST /lives/{id}/signals { clientId, peerId, signal }`,
  `GET /lives/{id}/signals?clientId&after` → `{ items, peers, next }`.
  `peers` (с `UserSummary`) получает только ведущий.
- `GET /lives/{id}/comments?after`, `POST /lives/{id}/comments { id, text }`.
- SSE `event: live` в общем потоке `/api/v1/direct/events`: `{ liveId }`.
- Ошибки: `LIVE_NOT_FOUND` 404, `LIVE_BUSY` / `LIVE_FULL` / `LIVE_ENDED` /
  `LIVE_STATE_CONFLICT` 409, `LIVES_UNAVAILABLE` 503.

## Риски

- Fan-out ограничен исходящим каналом и CPU ведущего (кодирование на
  каждого зрителя); поэтому лимит 10 и битрейт до 1 Мбит/с на зрителя.
- TURN в демосреде: без него зрители за NAT не подключатся — та же
  приёмка, что у звонков, на этапе 12.
- Сигнализация в памяти: после перезапуска API зрители переподключаются
  сами, ведущий продолжает эфир, если вернулся до истечения heartbeat.
- Общий файл с этапом 11: кольцо на аватаре. Эфир добавляет отдельный
  признак `live`, не меняя `storyRing`.
