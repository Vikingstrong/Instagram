## Как устроено

1. `POST /api/v1/posts/video` (multipart, поле `video`): файл пишется во
   временную приватную папку `MEDIA_ROOT/.incoming`, не в память; лимит
   10 загрузок в час снимается до чтения тела; больше 100 МБ —
   `413 VIDEO_TOO_LARGE` сразу при превышении.
2. Исходник проверяется ffmpeg (контейнер MP4/MOV/WebM, длительность до 90 с,
   сторона до 4096 px, настоящая видеодорожка, учёт поворота с телефона).
   Ошибка — `400 INVALID_VIDEO` / `VIDEO_TOO_LONG`, ничего не записано.
3. В одной транзакции создаются пост и медиа `PENDING`; ответ `201` со
   `status: "processing"`. Другим пост не виден (`visiblePost` требует
   `READY`), автору — виден со статусом.
4. В фоне (одна обработка за раз, таймаут 5 мин): H.264 main + AAC в MP4,
   длинная сторона до 1080 px, метаданные удалены, `+faststart`; обложка —
   кадр через тот же конвейер, что фото (`full` и `thumb`). Затем медиа
   `READY` с реальными размерами и длительностью. Исходник удаляется всегда.
5. Ошибка обработки — `failedAt`, автор видит `status: "failed"`; через час
   очистка удаляет пост и файлы. Удаление поста во время обработки
   отбрасывает результат. Перезапуск API помечает незавершённые видео
   неудачными (очередь в памяти, один процесс).
6. `GET /api/v1/media/{id}/video` — права проверяются на каждый запрос,
   один `Range` → `206`, за концом файла → `416`, `Cache-Control: private,
   no-store`, `nosniff`. Отзыв подписки прекращает выдачу на следующем же
   запросе диапазона.
7. `GET /api/v1/reels` — видеопосты, доступные зрителю (свои, одобренных
   подписок, публичных аккаунтов), только `READY`, новые сверху, доступ —
   до пагинации, без ранжирования.

Инструмент — `ffmpeg-static` 5.3.0 (ffmpeg 6.1.1), путь можно заменить
`FFMPEG_PATH`. ffprobe не нужен: проверка читает вывод самого ffmpeg, размеры
результата берутся из кадра-обложки. В `pnpm-workspace.yaml` пакету разрешена
установка бинарника. Сборки ffmpeg распространяются под GPL — для
портфолио допустимо, для коммерческого использования нужна другая сборка.

## Frontend

- `/create` принимает фото или видео; превью видео; прогресс загрузки
  через XMLHttpRequest («Загрузка… N%»); затем «Обрабатываем видео…» с
  опросом поста раз в 2 с и переходом к посту; ошибка обработки объяснена,
  можно выбрать другой файл; ошибка загрузки сохраняет файл и подпись.
- `VideoPlayer` — обычный `<video>` с обложкой, `playsInline`,
  `preload="metadata"`, без оптимизатора Next; недоступный файл —
  «Видео недоступно».
- Пост и лента показывают видео с управлением (в ленте не обёрнуто в
  ссылку); автору незавершённого видео — статус вместо плеера, лайки и
  комментарии открываются после готовности. В сетке профиля — значок видео.
- `/reels` — по одному ролику на экран с привязкой прокрутки; играет только
  ролик, видимый на 60 %, без звука до нажатия «Включить звук»; нажатие
  ставит на паузу; лайк, переход к комментариям; подгрузка за два ролика до
  конца; плавающая кнопка «Сообщения» здесь скрыта.

## Проверки

- `apps/api/src/media/video-processor.spec.ts` — перекодирование 1080p MOV
  со звуком (размер, кодеки, удаление метаданных, обложки), WebM без звука,
  отказ для длиннее 90 с, мусора, картинки, аудио, слишком широкого кадра;
  разбор вывода ffmpeg. Клипы генерирует сам ffmpeg — бинарных фикстур нет.
- `apps/api/src/media/byte-range.spec.ts` — разбор `Range`.
- `apps/api/test/video.integration-spec.ts` — сессия, CSRF, поле; обработка и
  видимость; 100 МБ+1, 95 с, мусор без остатков; сбой обработки и очистка;
  удаление во время обработки; перезапуск; Range 200/206/416 и заголовки,
  доступ чужого, подписчика и после отписки; Reels — доступность, порядок,
  фото и неудачные видео исключены, пагинация без дубликатов.
- `apps/web/features/posts/video.test.tsx`, `reels.test.tsx` — загрузка с
  прогрессом и ожиданием, ошибки, плеер, статус автора, лента и сетка,
  автозапуск видимого ролика, звук, подгрузка, лайк, пустое состояние.
- `apps/web/e2e/video.spec.mts` (desktop и mobile) — загрузка → обработка →
  пост → Reels другого пользователя с лайком → Range 206 через прокси →
  удаление → 404. В Chrome дополнительно проверяется воспроизведение;
  у Chromium из Playwright нет декодера H.264, поэтому в CI проверяется
  выдача, а не декодирование.

## Ограничения

- Обработка в процессе API: на слабом хостинге длинное видео займёт до
  минуты и нагрузит CPU; вынос в отдельный worker — кандидат для этапа 12.
- Публичные аккаунты попадают в Reels без подписки (предложение P-12,
  ждёт review).
