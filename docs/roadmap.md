## 2. Ответственность и API-first coordination

| Область                                                 | Основной владелец                               | Участие второго разработчика                                             |
| ------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------ |
| Backend, Prisma, миграции, инфраструктура, безопасность | Developer 1                                     | Developer 2 проверяет пригодность контрактов и пользовательский сценарий |
| Frontend, UI/UX, responsive, компоненты, frontend-тесты | Developer 2                                     | Developer 1 проверяет интеграцию, cookie и отсутствие обхода API         |
| `packages/contracts`                                    | Developer 1 организует изменение; оба согласуют | Developer 2 проверяет поля, ошибки, пагинацию и состояния UI             |
| Интеграция и критерии приёмки                           | Оба; Developer 1 координирует                   | Developer 2 ведёт браузерные проверки                                    |
| Продуктовые вопросы                                     | Оба принимают решение явно                      | Codex не выбирает правило вместо команды                                 |

Для каждого вертикального среза применяется один цикл:

1. **Контракт:** определить запросы/ответы, ошибки, права, ограничения и примеры. Включить нужные Zod-схемы и согласовать обоими разработчиками до зависимой реализации. Не проектировать весь API заранее.
2. **Параллельная реализация:** Developer 1 создаёт API и тесты, Developer 2 — интерфейс и тесты на фикстурах из того же контракта. Фикстуры не имитируют завершённый backend.
3. **Интеграция:** подключить реальный API, проверить cookie, ошибки, права и обновление данных; выполнить E2E. Только интегрированный результат закрывает срез.

Для уменьшения конфликтов один Issue/PR имеет одного владельца; оба могут использовать Codex в отдельных ветках или worktrees. Общие контракты, корневые scripts, lockfile и миграции изменяются согласованно, без одновременного редактирования одного участка двумя агентами. Зависимые ветки обновляются после merge контракта. Изменение контракта требует уведомления второго разработчика и обновления фикстур/тестов в том же срезе.

Каждая задача Codex содержит допустимые файлы, ссылки на требования, входной контракт, критерии приёмки и команды проверки. Developer 1 отвечает за этот workflow. Работа агента проходит человеческий review; миграции, политика доступа и auth требуют внимания обоих. План не требует изменения `AGENTS.md`.

### Этап 1. Foundation

Согласованный локальный baseline FND-01: [версии, порты 3000/4000,
маршрутизация `/api/v1/*`, workflow и ожидаемый smoke](development/foundation-baseline.md).
Это запись решения, а не подтверждение реализации proxy/readiness или приёмки
этапа. Review Developer 2 для FND-01 ещё требуется.
Backend FND-04: [readiness, Swagger и результаты проверки](development/api-readiness.md).
Ожидающий review FND-01/FND-03 не заменён автоматическими тестами и не мешает
продолжить backend-срез по согласованному контракту.
Локальное окружение FND-03: [PostgreSQL и Mailpit](development/local-environment.md).
Mailpit и PostgreSQL проверены в отдельных контейнерах Podman; прямой запуск Docker Compose и приёмка на второй машине ещё требуются. [Результаты](development/local-environment.md#результаты-проверки--2026-10-21).

- **Цель:** минимальная техническая вертикаль с реальным API и БД, пригодная для независимой работы над auth.
- **Backend / Developer 1:** закрепить технические версии, поднять PostgreSQL и тестовую почту, подготовить Prisma, конфигурацию окружения, readiness и общие контракты; настроить CI.
- **Frontend / Developer 2:** настроить REST-клиент, минимальный responsive shell и тестовые средства; проверить обращение к реальному API через общий origin.
- **Зависимости:** текущие scripts; выбор совместимых версий Prisma/PostgreSQL и способа локального запуска. Продуктовые вопросы не заменяются техническими настройками.
- **Definition of Done:** новый checkout запускается по повторяемой инструкции; browser/API/DB smoke и реальные автоматические проверки проходят в CI. Подробные условия — в разделе 6.
- **Необходимые тесты:** Zod-контракт, конфигурация, соединение с PostgreSQL, API readiness и его безопасная ошибка, браузерный smoke.
- **Риски и блокеры:** смешение API разных версий Prisma; ESM/TypeScript совместимость; отсутствующий browser runner; фиктивно зелёный CI без frontend-тестов.

### Этап 2. Auth и email

- **Цель:** полный цикл доступа к приложению по FR-01.
- **Backend / Developer 1:** контракты auth, первые прикладные Prisma-модели/миграции; хеширование паролей, сессии, verification/recovery, повторы писем, CSRF и лимиты чувствительных операций.
- **Frontend / Developer 2:** формы регистрации/входа/восстановления, подтверждение email, ожидающие и ошибочные состояния, управление сессией и очистка кеша при logout.
- **Зависимости:** P-01/P-02/P-03 и auth-часть P-09 согласованы владельцем. По разрешению от 2026-10-22 реализация начинается до FND-08; приёмка Foundation остаётся обязательной до окончательного закрытия этапа 2. Review затронутых контрактов и миграций сохраняется.
- **Definition of Done:** два тестовых пользователя проходят auth через реальные письма тестового адаптера; неподтверждённый пользователь не получает защищённые данные; logout прекращает сессию; recovery-токен нельзя использовать повторно. Это не считается завершением сценария публичной портфолио-почты до этапа 12.
- **Необходимые тесты:** уникальность и конкуренция регистрации, истечение/погашение токенов, одновременный reset, CSRF, отзыв сессии, отсутствие раскрытия email; браузерный полный auth-flow.
- **Риски и блокеры:** FND-08 перед окончательной приёмкой, review HTTP-контракта и DB-правил идентичности; сбой доставки; расхождение cookie в dev и deployment. Отзыв всех сессий после reset и ограничения auth-полей согласованы в FR-01. Сроки сессий/токенов и параметры хеширования определяет Developer 1 как техническую конфигурацию до реализации.

### Этап 3. Профиль, поиск и подписки

- **Цель:** пользователь находит другого пользователя, редактирует профиль и управляет отношениями подписки.
- **Backend / Developer 1:** профиль и регистронезависимый поиск; разрешённая сводка приватного профиля; запросы/одобрение/отклонение, отписка, удаление подписчика и утверждённые переходы приватности.
- **Frontend / Developer 2:** текстовый профиль/настройки, поиск, счётчики и Follow/Requested/Following, управление запросами; состояния отсутствия/запрета доступа.
- **Зависимости:** этап 2; P-04/P-05/P-06/P-09 и применимая часть P-07. Загрузка аватара выполняется на этапе 4; FR-02/03 пока не закрываются целиком.
- **Definition of Done:** публичная подписка создаётся сразу, приватная — после одобрения; дубликаты и подписка на себя невозможны; изменения профиля разрешены владельцу. Незавершённые продуктовые ветки явно блокируют закрытие затронутого среза.

### Этап 7. Direct: realtime и восстановление

Покупка/вывод реальных денег остаются вне среза.
- **Необходимые тесты:** получение до и после 00:00, изменение времени устройства, календарные переходы и граница 19:00 UTC / 00:00 следующей даты Душанбе, параллельные запросы/вкладки, повтор запроса после сетевого сбоя, недостаточный баланс, конкурентные подарки, равенство списания и зачисления, откат обеих сторон при ошибке, права на эфир и завершение эфира; реальные PostgreSQL-транзакции и browser E2E.
- **Блокеры:** контракт кошелька ещё не согласован; каталог, цены и оставшиеся правила подарков не определены. Часовой пояс уже подтверждён: `Asia/Dushanbe` (UTC+5). Не заменять календарный сброс таймером «через 24 часа после получения».

- [ ] `pnpm check-types`, `pnpm lint`, `pnpm build`, существующие API-тесты и новые явные contract/frontend/browser проверки проходят локально и в CI; нет ложных PASS из-за отсутствующих scripts.

- [ ] Оба разработчика понимают владельцев общих файлов и порядок «контракт → параллельная реализация → реальная интеграция/E2E»; критические дефекты Foundation закрыты.

## 8. Общее Definition of Done и контроль плана

Функциональный срез закрывается, когда контракт согласован, API и UI интегрированы, нужные миграции проверены, сценарий PRD работает на реальных зависимостях, негативные security-тесты проходят, CI запускает нужные проверки и оба разработчика приняли результат. Незавершённый UI на фикстурах, успешный запрос из API-клиента без браузерной интеграции или один стартовый тест не являются завершённым срезом.

После каждого принятого этапа команда уточняет оставшийся объём по фактическим результатам и скорости. Новые оценки и Issues появляются только для ближайшего среза. Изменение продукта сначала согласуется, затем отражается в его контракте и задачах; порядок не используется для незаметного изменения утверждённой архитектуры.
