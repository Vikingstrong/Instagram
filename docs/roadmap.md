# Instagram Clone — Engineering Roadmap

**Основание:** [PRD v0.3](product/PRD.md) и [Architecture Overview](architecture/overview.md).
**Статус:** план реализации; перечисленные результаты ещё не достигнуты, кроме явно отмеченной существующей основы.

План рассчитан на двух разработчиков, использующих первый Codex, другой claud code. Он задаёт восемь последовательных контрольных этапов без календарных обещаний: доступность команды и её скорость пока неизвестны. Только Foundation детализирован до предлагаемых GitHub Issues. Продуктовые требования остаются в PRD, технические решения — в Architecture Overview.

## 1. Исходное состояние

| Уже существует                                                                           | Ещё предстоит реализовать                                      |
| ---------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| `apps/web`: Next.js, Tailwind, конфигурация shadcn/ui; главная страница пока пустая      | Прикладной UI, формы, REST-клиент, SSE-клиент и frontend-тесты |
| `apps/api`: стартовый NestJS с `GET /` и ответом `Hello World!`                          | Предметные модули, авторизация, media и Direct                 |
| Единый pnpm workspace/lockfile, Turborepo, Node.js в `.nvmrc`                            | Локальная PostgreSQL, Prisma и процесс миграций                |
| Корневые `dev`, `dev:web`, `dev:api`, `check-types`, `lint`, `build`, `test`, `test:e2e` | `packages/contracts`, Zod-интеграция и контрактные проверки    |
| Vitest/Supertest: один стартовый unit-тест и один API e2e-тест                           | Прикладные интеграционные, security и браузерные тесты         |

CI configuration не обнаружена; у web нет test-script. Пустой `packages/` не означает наличие shared packages. Результаты прошлых проверок инфраструктуры не заменяют проверку нового функционального среза.

Сохраняются утверждённые решения: модульный монолит, PostgreSQL + Prisma, REST, Zod, cookie-сессии в БД, приватное media, REST + SSE и один процесс API. Обязательные `AccessModule`/`JobsModule`, Redis, брокер сообщений и микросервисы в план не добавляются.

## 2. Ответственность и API-first coordination

| Область                                                 | Основной владелец                               | Участие второго разработчика                                             |
| ------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------ |
| Backend, Prisma, миграции, инфраструктура, безопасность | Developer 1                                     | Developer 2 проверяет пригодность контрактов и пользовательский сценарий |
| Frontend, UI/UX, responsive, компоненты, frontend-тесты | Developer 2                                     | Developer 1 проверяет интеграцию, cookie и отсутствие обхода API         |
| `packages/contracts`                                    | Developer 1 организует изменение; оба согласуют | Developer 2 проверяет поля, ошибки, пагинацию и состояния UI             |
| Интеграция и критерии приёмки                           | Оба; Developer 1 координирует                   | Developer 2 ведёт браузерные проверки                                    |
| Продуктовые вопросы                                     | Оба принимают решение явно                      | Codex не выбирает правило вместо команды                                 |

Для каждого вертикального среза применяется один цикл:

1. **Контракт:** определить запросы/ответы, ошибки, права, ограничения и примеры. Включить нужные Zod-схемы и согласовать обоими разработчиками до зависимой реализации. Не проектировать весь API заранее.
2. **Параллельная реализация:** Developer 1 создаёт API и тесты, Developer 2 — интерфейс и тесты на фикстурах из того же контракта. Фикстуры не имитируют завершённый backend.
3. **Интеграция:** подключить реальный API, проверить cookie, ошибки, права и обновление данных; выполнить E2E. Только интегрированный результат закрывает срез.

Для уменьшения конфликтов один Issue/PR имеет одного владельца; оба могут использовать Codex в отдельных ветках или worktrees. Общие контракты, корневые scripts, lockfile и миграции изменяются согласованно, без одновременного редактирования одного участка двумя агентами. Зависимые ветки обновляются после merge контракта. Изменение контракта требует уведомления второго разработчика и обновления фикстур/тестов в том же срезе.

Каждая задача Codex содержит допустимые файлы, ссылки на требования, входной контракт, критерии приёмки и команды проверки. Developer 1 отвечает за этот workflow. Работа агента проходит человеческий review; миграции, политика доступа и auth требуют внимания обоих. План не требует изменения `AGENTS.md`.

### Этап 1. Foundation

- **Цель:** минимальная техническая вертикаль с реальным API и БД, пригодная для независимой работы над auth.
- **Backend / Developer 1:** закрепить технические версии, поднять PostgreSQL и тестовую почту, подготовить Prisma, конфигурацию окружения, readiness и общие контракты; настроить CI.
- **Frontend / Developer 2:** настроить REST-клиент, минимальный responsive shell и тестовые средства; проверить обращение к реальному API через общий origin.
- **Зависимости:** текущие scripts; выбор совместимых версий Prisma/PostgreSQL и способа локального запуска. Продуктовые вопросы не заменяются техническими настройками.
- **Definition of Done:** новый checkout запускается по повторяемой инструкции; browser/API/DB smoke и реальные автоматические проверки проходят в CI. Подробные условия — в разделе 6.
- **Необходимые тесты:** Zod-контракт, конфигурация, соединение с PostgreSQL, API readiness и его безопасная ошибка, браузерный smoke.
- **Риски и блокеры:** смешение API разных версий Prisma; ESM/TypeScript совместимость; отсутствующий browser runner; фиктивно зелёный CI без frontend-тестов.

### Этап 2. Auth и email

- **Цель:** полный цикл доступа к приложению по FR-01.
- **Backend / Developer 1:** контракты auth, первые прикладные Prisma-модели/миграции; хеширование паролей, сессии, verification/recovery, повторы писем, CSRF и лимиты чувствительных операций.
- **Frontend / Developer 2:** формы регистрации/входа/восстановления, подтверждение email, ожидающие и ошибочные состояния, управление сессией и очистка кеша при logout.
- **Зависимости:** Foundation принят; согласованы применимые P-01, P-02, P-03 и P-09 из раздела 7.
- **Definition of Done:** два тестовых пользователя проходят auth через реальные письма тестового адаптера; неподтверждённый пользователь не получает защищённые данные; logout прекращает сессию; recovery-токен нельзя использовать повторно. Это не считается завершением сценария публичной портфолио-почты до этапа 8.
- **Необходимые тесты:** уникальность и конкуренция регистрации, истечение/погашение токенов, одновременный reset, CSRF, отзыв сессии, отсутствие раскрытия email; браузерный полный auth-flow.
- **Риски и блокеры:** правила сессий после reset и ограничения auth-полей; сбой доставки; расхождение cookie в dev и deployment. Сроки сессий/токенов и параметры хеширования определяет Developer 1 как техническую конфигурацию до реализации.

### Этап 3. Профиль, поиск и подписки

- **Цель:** пользователь находит другого пользователя, редактирует профиль и управляет отношениями подписки.
- **Backend / Developer 1:** профиль и регистронезависимый поиск; разрешённая сводка приватного профиля; запросы/одобрение/отклонение, отписка, удаление подписчика и утверждённые переходы приватности.
- **Frontend / Developer 2:** текстовый профиль/настройки, поиск, счётчики и Follow/Requested/Following, управление запросами; состояния отсутствия/запрета доступа.
- **Зависимости:** этап 2; P-04/P-05/P-06/P-09 и применимая часть P-07. Загрузка аватара выполняется на этапе 4; FR-02/03 пока не закрываются целиком.
- **Definition of Done:** публичная подписка создаётся сразу, приватная — после одобрения; дубликаты и подписка на себя невозможны; изменения профиля разрешены владельцу. Незавершённые продуктовые ветки явно блокируют закрытие затронутого среза.
- **Необходимые тесты:** права профиля, поиск/пагинация, конкурентные запросы и принятие, корректные состояния/счётчики, отзыв отношения; браузерный сценарий двух пользователей.
- **Риски и блокеры:** судьба подписчиков/запросов при смене приватности, видимость списков, блокировки и гостевой просмотр. Проверка доступа к настоящим изображениям завершается следующим этапом.

### Этап 4. Приватное media и публикации

- **Цель:** безопасный цикл одной фотографии и аватара с проверкой доступа к файлу.
- **Backend / Developer 1:** media-контракт и приватный адаптер; проверка/перекодирование файлов, удаление метаданных, размеры изображений; создание/удаление постов и очистка незавершённых загрузок. Политика постов переиспользуется при выдаче media.
- **Frontend / Developer 2:** создание поста, аватар, сетка профиля, post details, ошибки/повторы загрузки и удаление собственных постов; отображение защищённых изображений без общего optimizer-кеша.
- **Зависимости:** этап 3; P-08 и применимые лимиты P-09; выбор storage-адаптера и процессора изображений без изменения приватной модели хранения.
- **Definition of Done:** владелец публикует фото; права проверяются API на пост и файл; после удаления подписчика новые запросы приватного файла запрещены; ошибка загрузки не создаёт некорректный пост; аватар соответствует правилам сводки профиля.
- **Необходимые тесты:** содержимое/размер/пиксели файла, прямой URL, чужое удаление, доступ до/после отзыва, утечки кеша, сбой storage/БД и повторяемая очистка; браузерный publish-flow.
- **Риски и блокеры:** неутверждённые форматы и лимиты, отсутствие общей транзакции БД/storage, нагрузка обработки и случайная публичная выдача.

### Этап 5. Лента и взаимодействия

- **Цель:** интегрированная хронологическая лента с лайками и комментариями.
- **Backend / Developer 1:** выборка собственных постов/подписок с фильтром доступа до пагинации; стабильный курсор, лайки и комментарии с правами удаления из PRD.
- **Frontend / Developer 2:** страницы ленты и комментариев, пагинация, loading/empty/error; согласование локальных изменений с ответом API и откат при отказе.
- **Зависимости:** этап 4; P-09 и P-10. Лента остаётся внутри `PostsModule`, если выделение отдельного модуля не обосновано реальной сложностью.
- **Definition of Done:** пагинация не дублирует посты; отозванный контент не возвращается; повтор лайка безопасен; автор поста и автор комментария имеют предусмотренные права, посторонний — нет.
- **Необходимые тесты:** одинаковые timestamps и новые записи между страницами, фильтрация после отписки, конкурентные лайки, матрица удаления комментариев, браузерный feed → post → interaction.
- **Риски и блокеры:** ошибки курсора, оптимистический UI после потери доступа, удаление собственного комментария после отзыва доступа. Не вводить алгоритмическую ленту.

### Этап 6. Direct: сохранение и история

- **Цель:** устойчивый обмен текстом через REST до добавления realtime.
- **Backend / Developer 1:** контракты диалога/сообщений, уникальная пара участников, история с курсором; транзакционная отправка, `clientMessageId`, лимиты и авторизация участника.
- **Frontend / Developer 2:** список диалогов, история и отправка, состояния pending/error/retry; повтор использует прежний идентификатор, а не создаёт новую отправку.
- **Зависимости:** этап 2, идентификаторы/профильная интеграция этапа 3 и решения P-07/P-09. Лента и media не являются технической зависимостью Direct.
- **Definition of Done:** сообщение хранится при offline-получателе и после перезапуска; чужой диалог недоступен; потеря HTTP-ответа и повтор не создают дубликат. FR-09 ещё не завершён: появление сообщений без refresh обеспечивается этапом 7.
- **Необходимые тесты:** конкуренция создания диалога, повтор сообщения с тем же/иным payload, атомарность/порядок, права истории и пагинация; браузерная отправка и ручная повторная загрузка истории.
- **Риски и блокеры:** правила блокировок и незнакомых отправителей; спам; неатомарное обновление активности. Нельзя самовольно требовать подписку для начала Direct.

### Этап 7. Direct: realtime и восстановление

- **Цель:** довести FR-09 до приёмки практически мгновенной доставки и восстановления истории.
- **Backend / Developer 1:** авторизованный SSE-поток, готовность подписки, уведомление после commit, heartbeat, очистка ресурсов и закрытие при отзыве сессии.
- **Frontend / Developer 2:** один поток на вкладку, subscribe → REST sync, объединение по ID, reconnect/focus/периодическая сверка активного диалога, видимые состояния соединения.
- **Зависимости:** этап 6; возможность потоковых HTTP-ответов в выбранной среде. Индикаторы прочтения/набора не добавляются как обязательные.
- **Definition of Done:** два браузерных контекста обмениваются сообщениями без refresh; разрыв и потеря уведомления восстанавливаются из БД; logout прекращает поток; один процесс API не держит неограниченные буферы.
- **Необходимые тесты:** промежуток между подпиской и синхронизацией, reconnect, commit без уведомления, перезапуск API, отзыв/истечение сессии, медленный клиент; интеграция через настоящий proxy.
- **Риски и блокеры:** буферизация, idle timeout, ограничения хостинга и соединений браузера. Redis/дополнительные API-инстансы не являются решением этой итерации.

### Этап 8. Проверка MVP и deployment

- **Цель:** показать завершённые сценарии PRD в выбранной демосреде и подтвердить эксплуатационные ограничения.
- **Backend / Developer 1:** один API, контролируемые миграции, HTTPS/origin/proxy, приватный storage, рабочая почта, секреты, лимиты, безопасные логи, backup/restore и проверка восстановления.
- **Frontend / Developer 2:** mobile/desktop регрессия, все обязательные состояния, доступность основных действий, кеш при смене пользователя, полный пользовательский проход.
- **Зависимости:** принятые этапы 1–7; P-01/P-02/P-11 и все затрагивающие выпуск решения из раздела 7.
- **Definition of Done:** оба разработчика проходят критические сценарии в независимых сессиях; CI и deployment smoke зелёные; известные ограничения зафиксированы, блокирующие дефекты устранены. Нерешённый Must Have нельзя объявить выполненным.
- **Необходимые тесты:** полная API/browser security-регрессия, реальные cookie/media/email/SSE через HTTPS proxy, восстановление БД и проверка связности media; измерение задержек и ресурсов на согласованном демонстрационном сценарии без выдуманных SLA.
- **Риски и блокеры:** открытая регистрация без правил злоупотреблений/retention, несовместимый streaming-хостинг, ограничения провайдеров. В эту фазу не откладываются auth и приватность — они проверяются в каждом предыдущем срезе.

## 4. Параллельная работа и обязательное ожидание

| Можно выполнять параллельно                                                         | Что обязательно должно завершиться раньше                          |
| ----------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Подготовка окружения Developer 1 и UI/test harness Developer 2                      | Общие версии и соглашения Foundation                               |
| API и UI одного среза; frontend использует контрактные фикстуры                     | Согласованный контракт, права и применимые продуктовые правила     |
| UI следующего среза на фикстурах во время интеграции текущего                       | Утверждение его контракта; это не готовность реальной интеграции   |
| Backend media и формы upload; backend Direct и UI истории                           | Соответственно политика доступа/лимиты и контракт истории/отправки |
| Подготовка Direct после auth/профильных идентификаторов, если есть свободный ресурс | P-07/P-09 и свой контракт; завершение feed технически не требуется |
| Ранний выбор deployment-среды и проверка её streaming-возможностей                  | Для полноценной SSE-проверки нужен работающий этап 7               |

Рекомендуемый порядок контрольных точек остаётся 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Допускается ранняя подготовка независимых задач Direct, но один разработчик не получает одновременно два полноценных backend-среза или два frontend-среза. Основной приоритет — завершить интеграцию текущего среза. Итоговый выпуск ждёт все этапы, а не только последний начатый.

### Порядок работы внутри Foundation

1. Оба согласуют FND-01, затем контракт FND-02. Developer 2 может готовить UI/test harness после выбора инструментов, но зависимая логика использует только согласованную схему.
2. После контракта Developer 1 выполняет FND-03/FND-04; Developer 2 параллельно ведёт FND-05/FND-06 на фикстурах. Это основные две дорожки, без назначения Developer 1 нескольких одновременных задач.
3. Developer 1 подключает реальные команды в FND-07; Developer 2 завершает переключение тестов на API и исправляет frontend-интеграцию. FND-08 закрывается совместно.

Foundation не включает готовую регистрацию, профили, media, SSE или всю будущую схему БД. Проверяемый вертикальный результат здесь технический: браузер действительно достигает API, а API — PostgreSQL. Последующие этапы дают пользовательские функциональные срезы.

## 6. Критерии перехода ко второму этапу

Переход к реализации auth допускается после совместной приёмки Foundation:

- [ ] На обеих машинах выполнен запуск из чистого checkout по одной инструкции; Node/pnpm и выбранная версия Prisma согласованы, lockfile воспроизводим.
- [ ] Dev/test данные изолированы; `.env.example` отслеживается, реальные секреты — нет. Тестовый почтовый ящик доступен; продуктовый выбор демонстрационной почты не объявлен решённым автоматически.
- [ ] Web и API импортируют настоящий `packages/contracts`; fixture и живой readiness-ответ проходят Zod-схему.
- [ ] Prisma соединяется с реальной PostgreSQL. Процесс подготовки/применения будущих миграций понятен; завершение Foundation не заявляется как готовность auth-схемы.
- [ ] Browser smoke проходит цепочку через общий origin; для успешной проверки БД нельзя заменить fixture. При недоступной БД readiness корректно сообщает неготовность без секретов.
- [ ] `pnpm check-types`, `pnpm lint`, `pnpm build`, существующие API-тесты и новые явные contract/frontend/browser проверки проходят локально и в CI; нет ложных PASS из-за отсутствующих scripts.
- [ ] Согласованы блокирующие **этап 2** P-01/P-02/P-03 и auth-часть P-09. Если решение не принято, технический Foundation может быть принят, но зависимая реализация auth не начинается. Остальные продуктовые вопросы остаются привязаны к своим этапам.
- [ ] Оба разработчика понимают владельцев общих файлов и порядок «контракт → параллельная реализация → реальная интеграция/E2E»; критические дефекты Foundation закрыты.

До этого разрешена проработка auth-контракта с явными открытыми полями, но не реализация выдуманных продуктовых правил. Сам по себе зелёный CI Foundation не означает готовность к публичной регистрации.

## 7. Product decisions: отдельный реестр блокеров

Источник решений — [открытые вопросы PRD](product/PRD.md#7-remaining-open-decisions) и [уточнения архитектуры](architecture/overview.md#17-open-product-decisions). Оба разработчика согласуют продуктовый ответ и отдельно отражают его в PRD/архитектуре при реализации; текущая задача эти документы не изменяет. ## 8. Общее Definition of Done и контроль плана

Функциональный срез закрывается, когда контракт согласован, API и UI интегрированы, нужные миграции проверены, сценарий PRD работает на реальных зависимостях, негативные security-тесты проходят, CI запускает нужные проверки и оба разработчика приняли результат. Незавершённый UI на фикстурах, успешный запрос из API-клиента без браузерной интеграции или один стартовый тест не являются завершённым срезом.

После каждого принятого этапа команда уточняет оставшийся объём по фактическим результатам и скорости. Новые оценки и Issues появляются только для ближайшего среза. Изменение продукта сначала согласуется, затем отражается в его контракте и задачах; порядок не используется для незаметного изменения утверждённой архитектуры.
